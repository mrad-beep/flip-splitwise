# Splitwise (mini) — Flip Retail Assignment, Part B

An expense-splitting app: Flask REST API backend + React frontend, talking
only over HTTP.

## Running it

### Backend

```bash
cd backend
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
python run.py
```

Runs on `http://localhost:5000`. A local `splitwise.db` (SQLite) is created
automatically on first run — nothing else to configure.

Run the tests:

```bash
pytest tests/ -v
```

### Frontend

```bash
cd frontend
npm install
npm run dev
```

Runs on `http://localhost:5173` and expects the backend to already be running
on `http://localhost:5000` (see `src/api.js` for the base URL).

## API

| Method | Endpoint                              | Purpose                              |
|--------|----------------------------------------|---------------------------------------|
| POST   | `/api/users`                           | Create a user (`{name}`)              |
| GET    | `/api/users`                           | List users                            |
| POST   | `/api/groups`                          | Create a group (`{name, member_ids}`) |
| GET    | `/api/groups`                          | List groups                           |
| GET    | `/api/groups/<id>`                     | Group detail                          |
| POST   | `/api/groups/<id>/members`             | Add a member (`{user_id}`)            |
| POST   | `/api/groups/<id>/expenses`            | Add an expense                        |
| GET    | `/api/groups/<id>/expenses`            | List a group's expenses               |
| GET    | `/api/groups/<id>/balances`            | Net balances + simplified transactions|
| POST   | `/api/groups/<id>/settlements`         | Record a payment between two members  |
| GET    | `/api/groups/<id>/settlements`         | List a group's settlements            |

`POST /expenses` body: `{description, amount, paid_by, split_among}`.
`split_among` is an optional list of user ids; if omitted it defaults to
every member of the group. Splits are always equal among `split_among`
(per the assignment scope), but see "data model" below for why that's a
deliberate simplification and not a limitation of the schema.

Errors return `{"error": "..."}` with a 4xx status (400 for bad input, 404
for missing resources). Success returns the created/requested resource with
a 2xx status.

## Data model — how a split is stored

This is called out in the assignment as where most people go wrong, so here's
the reasoning:

- **Money is stored as integer cents** (`amount_cents`), not floats. Floats
  can't represent amounts like ₹33.33 exactly, and summing them across many
  expenses drifts. Cents are converted to/from decimal only at the API
  boundary (`to_cents()` in, `/100` out in `to_dict()`).
- **Every expense has its own `ExpenseSplit` rows** — one per person who
  owes something for that specific expense, each with its own
  `amount_cents`. The expense's `amount_cents` is *not* divided on the fly
  wherever it's needed; it's divided once, when the expense is created, and
  stored explicitly. That means:
  - The split is auditable — you can see exactly what each person owed for
    each expense, not just a formula applied later.
  - It costs nothing to move beyond "equal splits" later (unequal amounts,
    percentages, shares) — the schema already supports arbitrary per-user
    amounts; only the *calculation* used to populate them at creation time
    would need to change.
  - Balance calculation is a single pass over rows: no re-deriving who owes
    what from expense metadata.
- **Equal splits are cent-exact.** ₹10 split three ways is 334/333/333
  cents, not 333.33 repeating — see `equal_split_cents()` in
  `app/balances.py`. The remainder cent(s) go to the first N people rather
  than getting silently dropped or double-counted, so the split always sums
  back to the original amount exactly.
- **Settlements are their own table**, separate from expenses. A settlement
  isn't an expense (nothing was purchased), so it doesn't have splits — it's
  just "X paid Y this much," and it shifts both people's net balance.

## Balance calculation

`app/balances.py` is intentionally free of Flask/SQLAlchemy imports so the
math can be unit-tested without a database or app context.

1. **Net balance per user**: for every expense, the payer's net goes up by
   the full amount, and each split participant's net goes down by their
   share. Every settlement then shifts the payer's net up and the receiver's
   net down by the settled amount. The result is one number per user:
   positive = they're owed money, negative = they owe money.
2. **Debt simplification** (the bonus): rather than showing every pairwise
   debt generated by every expense, `simplify_debts()` greedily matches the
   biggest creditor against the biggest debtor, repeatedly, until everyone
   nets to zero. This is a standard heuristic — not provably minimal in
   every case, but a real improvement over listing raw pairwise debts, and
   is what the frontend's "who should pay whom" section shows.

`tests/test_balances.py` covers both directly, including a 3-person
multi-expense scenario that checks the simplified transactions, applied
back, actually zero everyone out.

## What was skipped (as instructed)

- Authentication — a name is all a "user" is.
- Deployment/production config — this runs with Flask's dev server; no
  Docker, no WSGI server, no environment-based config.
- Visual design — the frontend is functional and unstyled beyond basic
  layout/readability.
- Editing or deleting expenses/settlements once created.
- Multi-currency support.

## What I'd do next

- Allow non-equal splits (exact amounts or percentages) — the data model
  already supports it; only the request shape and a bit of validation would
  need to change.
- Edit/delete for expenses and settlements, with balances recomputing from
  the same `balances.py` logic (no duplicate math to keep in sync).
- Pagination on expense/settlement lists once a group has real history.
- Move from SQLite to Postgres and add Alembic migrations before this touches
  a second environment.
- A production WSGI server (gunicorn) and basic input rate limiting.

## On AI use

This implementation (backend, frontend, and tests) was built with AI
assistance. Anyone submitting this should treat that as a starting point,
not a finish line: per the assignment's condition, walk through every file,
be ready to explain *why* it's written the way it is (not just what it
does), and be able to change it live in an interview. The parts most worth
being able to defend on the spot are `app/balances.py` (the net-balance +
debt-simplification logic) and `app/models.py` (why splits are stored as
explicit rows in cents rather than computed from a formula).
